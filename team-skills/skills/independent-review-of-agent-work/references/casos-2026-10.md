# Casos de revisão (2026-10)

| Passo | Caso | Resultado |
|---|---|---|
| Fixar a base | Um PR de correção partia de um main anterior a outro PR acabado de entrar e que tocava no mesmo ficheiro. | `git merge-tree` mostrou o conflito; o autor fez merge do main no branch antes da revisão final. |
| Ler o código | Uma correção de cotações substituía um timestamp em falta por "agora". | Mudado para "em falta"; deixou de fabricar frescura. |
| Reproduzir | "77 testes passaram": no revisor falharam 2 porque o TMPDIR era tmpfs. "69 testes": falharam 6 porque o checkout tinha ficheiros com escrita para o grupo. | Em ambos os casos o código estava certo; ao reproduzir, percebeu-se que os testes dependiam do ambiente, e isso ficou registado. |
| Correr no host | O inventário de units de um PR de correção foi executado no host, só em leitura, antes do merge. | Confirmou que tratava units template e tmpfs. |
| Dados reais | O dryrun de uma correção do registo mostrou 58 entradas e 8 saídas indevidas. | Bloqueado; o head seguinte teve 58 entradas e 0 saídas e foi aprovado. |
| Dados reais | O dryrun de uma correção de retenções mostrou que 499 de 510 retenções US passavam a aviso, com os 11 controlos ainda retidos. | Aprovado com base nesta prova. |
| Olhar para os lados | Um motor de deploy recém-instalado adia pedidos perto de runs agendadas. | O veredito incluiu "fazer merge entre as 20:15 e as 21:15"; o deploy ficou verified à primeira. |
| Modos de falha | Num emissor de estado: o `OnSuccess=` bloqueava todos os componentes, era pedido um token a cada minuto e a verificação só olhava para o timer. | Três correções bloqueantes, cada uma com o teste esperado. |
| Passos humanos | Uma credencial externa (GitHub App) sem instruções no PR. | Acrescentada como item obrigatório antes da instalação. |
